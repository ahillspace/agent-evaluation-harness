01 / The rebuild

A consolidated application foundation.

The previous application already had adapters, SQLite storage, live observation, rescoring, and a CLI. The rebuild consolidates overlapping workflows and makes ownership explicit.

Before

Multiple execution paths

Workspace packages with separate web and campaign lifecycles.

Internal model: Project → Study → Experiment → Run → Attempt, plus batches and research sessions. Two database paths reflect different workflows.

After

One application core

Explicit contracts, shared operations, and replaceable infrastructure.

User model: Question bank → Blueprint → Run → Results. Evaluator revisions and score sets preserve how each answer was assessed.

One local engine with clear responsibilities.

The UI presents workflows. Application services enforce them. Infrastructure handles providers, storage, processes, and secrets. Dependency rules keep those responsibilities separate.

Sources: previous architecture, current architecture, and implementation entry points listed below.

What belongs to the rebuild, and what came afterward

Foundation

Unified execution

Shared operations, simpler domain model, explicit ownership, and per-run agent configuration export.

Evaluation expansion

Jev + stronger policies

Optional classification, editable judging profiles, and broader handling of answer variation and disputed references.

Platform work

macOS architecture

Keychain and POSIX process implementations. Native macOS acceptance still needs a real Mac.

Target expansion

External HTTP agents

Answer-only evaluation and a developer-owned adapter boundary. Agentforce and Copilot Studio are future adapters.

02 / Assessment

Stronger boundaries. Real tradeoffs.

What improves

  • Fewer concepts to coordinate. A single run lifecycle reduces translation between campaigns, experiments, and interactive runs.
  • Consistent automation. CLI and browser operations share the same application behavior and validation.
  • Clear ownership. The harness owns evaluation and immutable evidence; the researcher owns candidate changes.
  • Safer iteration. New evaluations produce new score sets while preserving the original execution evidence.
  • Defined extension points. Platforms, targets, connections, and judges have explicit contracts.

What costs something

  • Different isolation. The previous Docker/Podman tool-worker path was not carried forward.
  • Narrower deployment. The application is local-only. The CLI uses a running engine; authenticated remote hosting is no longer available.
  • Controlled extensions. Adapters are shipped by developers. Previous trusted local harness-plugin loading is not retained.
  • Migration remains explicit. Existing legacy data is not automatically converted. There is no packaged installer or standalone installed command.
  • Platform confidence is uneven. Windows and Linux checks exist; native macOS acceptance remains outstanding.

The architecture makes maintenance easier to reason about. It does not, by itself, prove that every evaluation is correct or every platform is production-ready.

04 / A shared UI standard

A consistent system across every screen.

Keep the harness’s own concepts. Borrow Linear’s restraint, predictable controls, compact layouts, and keyboard-friendly navigation.

Area Current direction Proposed standard Required change
Visual language Existing dark surfaces, brighter accents, and page-specific styling. Neutral charcoal surfaces, restrained violet emphasis, consistent text and spacing. One token set for color, typography, spacing, radius, elevation, and focus. Remove superseded styles.
Application shell Navigation and page layouts reflect separate feature work. Stable sidebar, compact location header, consistent page actions and tabs. One shared shell and page layout contract. Preserve the user’s location across detail views.
Run observation Live observation and saved evidence already exist. Question queue, detail panel, and evaluation inspector with the same structure for live and saved runs. Compose existing data into shared panels. Define loading, empty, interrupted, stale, and terminal states.
Run setup Multiple sections with advanced settings and target-specific choices. Clearly named sections, required markers, concise help, and relevant fields only. Shared form controls, inline validation, help popovers, and progressive disclosure. No managed-agent fields for HTTP targets.
Banks and results Feature-specific lists and detail screens. Consistent density, filtering, selection, and contextual detail previews. Reusable list and inspector patterns. Saved views would need explicit preference persistence, not just CSS.
Commands Visible actions and CLI automation. Discoverable command menu and a small set of predictable keyboard shortcuts. A UI action registry with availability rules, shortcut help, focus restoration, and conflict handling.
Feedback and controls Run controls and errors exist. Clear pending states, meaningful error text, durable failures, and quiet success feedback. Unified status language and feedback components. Explain pause, halt, cancel, and remote cancellation limits.
Accessibility Must be evaluated across existing screens. Readable contrast, visible focus, full keyboard access, and status beyond color. Accessible primitives, screen-reader announcements, reduced motion, and narrow-screen layouts.

Use a system sans-serif stack, 4px spacing increments, restrained 6–8px radii, and limited semantic color. Compact layouts must retain readable text and usable controls.

Implementation sequence

  1. Define the interface contract

    Inventory pages, states, actions, and shared primitives. Agree on tokens and accessibility requirements before changing screens.

  2. Build the observation reference

    Use real engine events and saved artifacts. Cover managed and HTTP targets, all run states, and narrow layouts.

  3. Apply the same system everywhere

    Move setup, question banks, results, connections, and settings onto shared components. Delete replaced styling and wiring.

  4. Review the complete experience

    Review architecture, keyboard behavior, visual consistency, and end-to-end tasks. Reject page-specific exceptions without a clear reason.

Keep the separation earned by the rebuild.

Layout and presentation belong in the web layer. Existing run, scoring, and adapter rules stay in application contracts. New persisted preferences need an explicit application operation.

Design tradeoff: dense interfaces suit frequent users but can hide meaning. Keep plain labels and contextual help; use shortcuts as an enhancement. No Linear issue-tracking hierarchy is needed.

05 / What changes for the end user

The practical before and after.

Only changes people encounter while setting up, running, reviewing, or operating the application.

01
Simplified

A consolidated run workflow

The familiar Question banks / Run / Results workflow remains. Run setup and reuse now follow one consistent workflow rather than separate campaign and interactive paths.

02
Retained and consolidated

Watch and control runs

Live observation, saved evidence, pause, halt, resume, and cancel remain available. These were not invented by the rebuild.

03
Retained and expanded

Improve scoring after a run

Review answers and rescore saved evidence with revised evaluators. Broader policies handle rounding, ties, aliases, and disputed references. False failures still require review.

04
Added after the rebuild

Add optional Jev classification

Deterministic evaluation stays the default. Existing optional LLM judging remains available. Jev adds a separate classification assessment with editable instructions and independently recorded results.

05
New export; blueprint reuse retained

Take the tested configuration with you

Export a run’s agent settings and system prompt as JSON. Credentials use placeholders. Reusing previous runs as setup blueprints remains available.

06
Added after the rebuild

Evaluate an external HTTP agent

Send questions to an endpoint and score returned answers. Preview request mapping before running. Internal tools, reasoning, and system-prompt editing are unavailable.

07
Automation changed

Use the CLI for the same workflows

Automation uses JSON operations shared with the browser. The CLI now requires the local engine. An installed standalone command is not yet packaged.

08
Removed paths

Local operation has clearer limits

The old container tool-worker option, authenticated remote hosting, and trusted local harness-plugin loading are not carried forward.

09
Current limitation

Legacy history needs deliberate migration

Old data is preserved separately, not automatically converted. Expect an explicit migration decision before relying on previous history in the new application.

10
Implemented groundwork; acceptance pending

macOS support needs final native verification

Keychain and process support are implemented. A real Mac acceptance pass is still needed before claiming fully verified macOS support.

11
External-agent limitation

Stopping locally may not stop remotely

HTTP cancellation cannot guarantee remote execution stopped. The initial HTTP adapter evaluates completed responses, without remote trace ingestion or streaming.

12
Proposed, not implemented

One consistent interface

The Linear-inspired design shown above would unify navigation, forms, lists, observation, help, and keyboard actions. Agentforce and Copilot Studio remain future integrations.
